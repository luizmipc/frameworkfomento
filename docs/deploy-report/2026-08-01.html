Achados desta rodada

Nível 0 de maturidade CI/CD: nenhum pipeline automatizado

🔴 Bloqueante/Alto

O que foi encontrado: .github/workflows/ não existe no repositório — nenhum build, lint ou teste roda automaticamente em push/PR, e não há pipeline de deploy nem rollback.

Evidência:

$ find .github/workflows -type f 2>/dev/null; echo "exit:$?"
exit:1
$ ls -la .github
ls: cannot access '.github': No such file or directory

Impacto: todo gate de qualidade (lint, testes, futuramente auditoria de segurança) depende hoje de alguém rodar ./run_tests.sh localmente antes de commitar — não há rede de segurança se esse passo for esquecido ou pulado, e não há forma automatizada de saber se um push quebrou o build antes de alguém notar manualmente.

Recomendação: criar um workflow mínimo em .github/workflows/ que rode ./run_tests.sh (lint + suíte Django) em todo push/PR — Nível 1 de maturidade. Evoluir depois para Nível 2 (mesmo workflow, mas como gate obrigatório de PR) e só então considerar Nível 3 (deploy automatizado com rollback), quando houver ambiente de deploy real.

Janela recomendada de correção: até 30 dias.

Fator do 12-Factor violado: nenhum fator específico do 12-Factor cobre CI/CD em si — este achado é a régua de maturidade de pipeline descrita nas Táticas de deployment do devops, não uma violação de um dos Doze Fatores.

Servidor de desenvolvimento do Django (runserver) como processo de produção

🔴 Bloqueante/Alto

O que foi encontrado: o CMD do Dockerfile roda uv run manage.py runserver — o servidor de desenvolvimento single-threaded do Django, não um servidor WSGI/ASGI de produção (gunicorn/daphne/uvicorn).

Evidência:

Dockerfile:25:CMD uv run manage.py runserver ${DJANGO_HOST:-0.0.0.0}:${DJANGO_PORT:-8000}

Impacto: runserver não foi projetado para produção — não lida bem com concorrência real, recarrega código a cada request em modo autoreload, e não tem as garantias de robustez de um servidor WSGI/ASGI dedicado. O comando "funciona" (a aplicação responde HTTP 200 e passa o HEALTHCHECK), mas isso não substitui ter o mesmo tipo de processo em dev e produção — o ângulo de segurança desse mesmo achado (exposição de banner de servidor, headers) já está documentado no cybersec-report, não repetido aqui.

Recomendação: trocar o CMD de produção por um servidor WSGI/ASGI real (gunicorn ou uvicorn, conforme a stack), mantendo runserver apenas para o fluxo de desenvolvimento local (fora do Dockerfile de produção, ou por variável/target de build separado).

Janela recomendada de correção: antes do próximo deploy real.

Fator do 12-Factor violado: X. Dev/prod parity — mesmo backing service, mas não o mesmo tipo de processo entre dev e produção.

Sem estágio de release automatizado (migrate/collectstatic ausentes)

🔴 Bloqueante/Alto

O que foi encontrado: nem o CMD do Dockerfile nem nenhum entrypoint dedicado rodam manage.py migrate ou collectstatic antes do processo subir — não existe nenhum script de entrypoint no repositório.

Evidência:

$ find . -iname "entrypoint*" -o -iname "docker-entrypoint*"
./app/.venv/lib/python3.14/site-packages/semgrep/console_scripts/entrypoint.py   # da lib semgrep, não da app
$ cat Dockerfile   # CMD é só "uv run manage.py runserver ...", sem migrate/collectstatic antes

Impacto: o estágio de release (build + config do ambiente, incluindo migração de schema) fica implícito/manual — alguém precisa lembrar de rodar migrate à parte antes ou depois de subir o container. Hoje o schema é trivial (scaffold Django, SQLite) e isso passa despercebido, mas assim que houver migrations reais de app de negócio, um deploy sem esse passo sobe com schema desatualizado sem nenhum aviso.

Recomendação: adicionar um passo de release explícito — migrate (e collectstatic, quando houver arquivos estáticos de produção) rodando automaticamente antes do processo principal, via entrypoint script ou etapa dedicada do pipeline de CI/CD do achado 1.

Janela recomendada de correção: antes do próximo deploy real.

Fator do 12-Factor violado: separação build/release/run — o estágio de release (que inclui migração de banco) não existe como passo distinto e automatizado.

Shutdown não gracioso: CMD em shell-form não repassa SIGTERM

🟡 Médio

O que foi encontrado: o CMD do Dockerfile está em shell-form (CMD uv run manage.py runserver ..., não a forma JSON ["uv", "run", ...]), o que faz o processo real rodar como filho de um /bin/sh -c — sinais como SIGTERM enviados pelo Docker no docker stop não chegam garantidamente ao processo Django.

Evidência: confirmado tanto pelo warning do próprio docker build quanto por teste real de docker stop nesta rodada:

$ docker build --no-cache -t frameworkfomento-deploy-check:2026-08-01 .
...
1 warning found (use docker --debug to expand):
 - JSONArgsRecommended: JSON arguments recommended for CMD to prevent unintended behavior related to OS signals (line 25)

$ docker compose up -d --build && time docker stop frameworkfomento-app-1
docker stop frameworkfomento-app-1  0.01s user 0.01s system 0% cpu 10.283 total
$ docker inspect frameworkfomento-app-1 --format='ExitCode:{{.State.ExitCode}}'
ExitCode:137

Impacto: docker stop levou os 10s completos do período de graça padrão e terminou com ExitCode 137 (o container foi morto a força via SIGKILL, não encerrado graciosamente via SIGTERM). Em produção, isso significa que todo redeploy/scale-down mata requests em andamento em vez de drená-las — nenhum shutdown gracioso de fato acontece, mesmo a aplicação "funcionando" no dia a dia.

Recomendação: trocar o CMD para a forma JSON/exec (CMD ["uv", "run", "manage.py", "runserver", ...], ajustando conforme o servidor de produção escolhido no achado 2) para que o processo principal receba sinais do Docker diretamente como PID 1.

Janela recomendada de correção: até 30 dias.

Fator do 12-Factor violado: IX. Disposability — shutdown deve ser gracioso ao receber SIGTERM, não depender do container ser morto à força após o timeout.

Imagem de produção carrega dependências de desenvolvimento

🟢 Baixo

O que foi encontrado: o Dockerfile roda uv sync --locked (sem --no-dev) na etapa final, instalando também o grupo dev de app/pyproject.toml (ruff, bandit, semgrep — este último traz de tabela mcp, opentelemetry-* e dezenas de outras dependências transitivas) dentro da imagem que também roda em produção.

Evidência:

$ cat app/pyproject.toml
[dependency-groups]
dev = [
    "ruff>=0.16.1",
    "bandit>=1.8.0",
    "semgrep>=1.170.0",
]

$ docker build --no-cache -t frameworkfomento-deploy-check:2026-08-01 .
...
 + mcp==1.23.3
 + opentelemetry-api==1.37.0
 + opentelemetry-sdk==1.37.0
 + semgrep==1.172.0
 (... 76 pacotes resolvidos ao todo)

$ docker images frameworkfomento-deploy-check:2026-08-01
IMAGE                                      DISK USAGE
frameworkfomento-deploy-check:2026-08-01   1.37GB

Impacto: a imagem que roda em produção é bem maior do que precisaria ser — o app real depende só de django==6.0.7. Isto é uma medição de baseline honesta (o repo não define um budget de tamanho de imagem, então não há um limite "estourado" aqui), não uma auditoria de vulnerabilidade — quantidade de pacotes instalados como fator de superfície de ataque é ângulo do trivy/ cybersecurity-blue (já rodou e reportou 0 vulnerabilidades em app/uv.lock nesta mesma imagem, ver cybersec-report).

Recomendação: usar uv sync --locked --no-dev (ou equivalente por grupo) na etapa final do Dockerfile de produção, mantendo o grupo dev só para o ambiente de desenvolvimento/CI.

Janela recomendada de correção: até 90 dias.

O que já está pronto para produção

  • Usuário não-root confirmado — Dockerfile cria appuser (uid 1000) e roda o processo com USER appuser, não root.
  • HEALTHCHECK configurado e confirmado healthy — subiu via docker compose up -d --build e, após o --start-period=5s, docker inspect reportou {"Status":"healthy","FailingStreak":0,...} nesta rodada.
  • Config/segredos só via variável de ambiente (Fator III) — DJANGO_SECRET_KEY, DJANGO_DEBUG, DJANGO_ALLOWED_HOSTS, DJANGO_HOST, DJANGO_PORT todos lidos de env var, todos com exemplo documentado em .env.example — nenhuma lacuna encontrada nesta rodada.
  • docker compose config resolveu sem erro — sintaxe válida, todas as variáveis do docker-compose.yml resolvidas contra .env.
  • Build reprodutível do zero — docker build --no-cache completou com sucesso em ~44s, sem falha de dependência ou de camada.
  • Aplicação responde de verdade — curl http://localhost:8000/ devolveu HTTP 200 nesta rodada, subida via docker compose igual a como um deploy real subiria.

Para quem resolver

Todos os achados desta rodada são de prontidão operacional — roteados ao dev via /kanban-sync → "Criar nova tarefa" → "A partir de um relatório existente" → docs/deploy-report/. Nenhum achado aqui se sobrepõe à lente de segurança já coberta pelo cybersecurity-blue (ver cybersec-report).

  • Achado 1 — criar workflow mínimo em .github/workflows/ (Nível 1 de maturidade CI/CD).
  • Achado 2 — trocar runserver por servidor WSGI/ASGI de produção.
  • Achado 3 — automatizar migrate/collectstatic como estágio de release.
  • Achado 4 — mudar CMD para forma JSON/exec para shutdown gracioso.
  • Achado 5 — separar dependências de dev da imagem de produção (--no-dev).

Nenhuma decisão de release-readiness sai deste relatório — isso é do scrum-master, que usa este documento como insumo, não como gate em si.

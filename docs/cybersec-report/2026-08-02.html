Auditoria de segurança da aplicação real (app/, Django 6.0.7), em 2026-08-02 — arquivo novo, primeira rodada deste dia. Aplicação subida via docker compose up -d --build, confirmada respondendo HTTP 200 em http://localhost:8000/ e docker inspect reportando healthy via o HEALTHCHECK adicionado no dia anterior. Os sete testes de shortcuts/security-test.sh rodaram sem argumentos, na ordem canônica do script (gitleaks → bandit → semgrep → deps → trivy → django-check → zap), executados diretamente por este agente contra o ambiente local (não a partir de um relato de terceiros). Achados desta rodada

A05:2021 — manage.py check --deploy não roda: gap de tooling no próprio script de auditoria

🟢 Baixa — CVSS 0 (gap de observabilidade, não vulnerabilidade do app)

Ferramenta: execução direta de shortcuts/security-test.sh django-check, reproduzida por este agente. O comando crasha antes de rodar o check de verdade:

django.core.exceptions.ImproperlyConfigured: DJANGO_SECRET_KEY must be set via
environment variable when DEBUG=False. Refusing to start with the insecure
development fallback in production.

Causa raiz confirmada lendo shortcuts/security-test.sh (função run_django_check, linha ~80): ela chama uv run manage.py check --deploy sem carregar .env primeiro. Sem DJANGO_DEBUG/DJANGO_SECRET_KEY no ambiente do shell, DEBUG cai no default seguro (False, por design da task A022) e o fail-safe da task A023 dispara antes do check --deploy sequer rodar. Isto é efeito colateral do próprio endurecimento de segurança: o script de auditoria perdeu cobertura de um dos sete testes que ele mesmo define, sem avisar de forma clara que o resultado é "não foi possível medir" e não "0 warnings, passou limpo". run_tests.sh já resolve o mesmo problema para a suíte de testes Django (carrega .env linha a linha antes de rodar) — shortcuts/security-test.sh deveria fazer o mesmo antes de run_django_check().

ASVS: não é uma violação de requisito da aplicação em si — é um gap de processo de verificação (a ferramenta de auditoria, não o alvo auditado). Sem visibilidade sobre os warnings reais de check --deploy nesta rodada, portanto: não afirmamos que esse teste passou, apenas que não pôde ser medido.

Observação (não coberta por nenhum teste do script) — self-check de segurança da task A023 não é executado automaticamente

🟢 Baixa — CVSS 0 (gap de detecção/regressão, não vulnerabilidade ativa)

Como foi encontrado: STRIDE leve sobre o fluxo de verificação de segurança em si (Repudiation/Detection) — não veio de nenhuma ferramenta do security-test.sh. Confirmado rodando uv run manage.py test localmente com .env carregado: Ran 0 tests in 0.000s / NO TESTS RAN. app/config/tests.py (o self-check demo() da task A023, que valida o fail-safe do SECRET_KEY via subprocess) é um script standalone, não uma django.test.TestCase — o descobridor de testes do Django só coleta subclasses de TestCase, então esse arquivo nunca roda via manage.py test. E run_tests.sh (lido nesta rodada) também não o chama diretamente — só roda lint.sh e manage.py test. Resultado: o único self-check automatizado da correção mais importante do dia anterior (fail-safe de SECRET_KEY) existe no repo mas nunca é executado por nenhum gate automatizado — só se um humano lembrar de rodar uv run python config/tests.py manualmente.

Recomendação concreta: ou (a) adicionar uma chamada a uv run python config/tests.py em run_tests.sh (menor diff, mesma dependência zero), ou (b) converter demo() em um método de django.test.TestCase real para que manage.py test o descubra nativamente (mais idiomático, sem precisar tocar run_tests.sh). Qualquer uma resolve; não há uma "certa" — é decisão do dev.

ASVS: V7.4 (verificação de segurança deveria fazer parte de gate automatizado, não depender de execução manual lembrada).

A05:2021 — Cross-Origin-Resource-Policy header ausente (residual do ZAP)

🟢 Baixa — CVSS 2.6

Ferramenta: OWASP ZAP Baseline, alerta 90004 (família "Cross-Origin-*"), WARN-NEW x1 em http://localhost:8000/. Este é um achado residual e diferente do que aparecia no dia anterior sob o mesmo ID de regra: antes era "Cross-Origin-Embedder-Policy Header Missing" (2 hits) — corrigido pela task A025, que adicionou Cross-Origin-Embedder-Policy: require-corp em app/config/middleware.py. Agora o ZAP reclama de um cabeçalho diferente da mesma família: Cross-Origin-Resource-Policy (CORP), que o middleware atual não seta — confirmado lendo app/config/middleware.py, que só define Permissions-Policy, Cross-Origin-Embedder-Policy e Content-Security-Policy-Report-Only.

CVSS 3.1: AV:N/AC:H/PR:N/UI:R/S:U/C:L/I:L/A:N ≈ 2.6 (Baixa) — defesa em profundidade contra vazamento cross-origin de recursos que hoje não existem (scaffold sem API/assets sensíveis ainda); mesmo raciocínio de exploitability do achado de CSP do dia anterior.

ASVS: V14.4 (cabeçalhos de resposta HTTP). Resolução: adicionar Cross-Origin-Resource-Policy: same-origin (ou same-site, a decidir pelo dev conforme necessidade de assets cross-origin) no mesmo middleware que já seta os outros dois.

O que já está bem protegido

  • RESOLVIDO e reconfirmado — Dockerfile root + sem HEALTHCHECK (achados A021/A026, 2026-08-01): trivy agora reporta 0 misconfigurações no Dockerfile (eram 2) — a mesma ferramenta que achou o problema confirma a correção. docker inspect reporta healthy nesta rodada.
  • RESOLVIDO e reconfirmado — DEBUG/SECRET_KEY/ALLOWED_HOSTS/cookies (achados A022–A024, 2026-08-01): lidos de variável de ambiente com defaults seguros; fail-safe de SECRET_KEY testado ao vivo nesta rodada (o crash do achado A05 acima É o fail-safe funcionando corretamente — só não dava para medir o check --deploy por causa dele).
  • Melhoria real e mensurável em cabeçalhos HTTP — ZAP foi de 62 PASS/5 WARN-NEW (dia anterior) para 63 PASS/4 WARN-NEW nesta rodada; Permissions-Policy e CSP (report-only) saíram da lista de WARN e viraram PASS, confirmando que o middleware novo (task A025) funciona.
  • Zero segredos versionados, zero SAST, zero SCA relevante — gitleaks (61 commits, 0), bandit (0 Medium/High) e semgrep (0 findings) confirmam que o código-fonte segue limpo; trivy confirma 0 vulnerabilidades em app/uv.lock.
  • DAST baseline limpo de injeção — 0 FAIL em 4 URLs testadas; todos os WARN restantes são de cabeçalho ausente ou informativos, não injeção/autenticação/sessão quebrada.

Isto NÃO é uma afirmação de que toda a aplicação está segura — apenas que, dentro do que os sete testes de shortcuts/security-test.sh cobrem (e, nesta rodada, um deles não cobriu de fato — ver achado A05), nada de Crítico ou Alto foi encontrado. A aplicação ainda é majoritariamente o scaffold do Django, sem app de negócio implementado — a superfície real de ataque crescerá conforme features forem adicionadas.

Para quem resolver

Achados com correção de código/config real, para virar tarefa via /kanban-sync → "Criar nova tarefa" → origem "A partir de achados de segurança de docs/cybersec-report/" (todos vão para o dev):

  • Baixa: carregar .env em shortcuts/security-test.sh antes de run_django_check(), mesmo padrão já usado em run_tests.sh — sem isso, manage.py check --deploy nunca roda de verdade contra este projeto outra vez.
  • Baixa: conectar o self-check config/tests.py (task A023) a um gate automatizado — chamada em run_tests.sh ou conversão para TestCase real, decisão do dev.
  • Baixa: adicionar Cross-Origin-Resource-Policy ao middleware em app/config/middleware.py, junto dos outros cabeçalhos já setados ali.
  • Informativa, sem tarefa dedicada recomendada: os 8 achados bandit Low em config/tests.py/settings.py são ruído esperado de um script de auto-verificação de dev (subprocess com args fixos, assert em script standalone, valores de teste que não são segredos reais) — não recomendamos ação isolada só para silenciar o bandit aqui; se o achado acima (conectar a um gate real) for implementado como conversão para TestCase, os assert naturalmente virariam self.assertX, resolvendo isso de graça.
  • Informativa: atualizar semgrep (puxaria mcp mais novo) quando conveniente, junto de rotina de dependências de dev — inalterado desde o dia anterior.

Nenhuma decisão de compliance formal (ex.: LGPD) nem de release-readiness sai deste relatório — isso é do product-owner e do scrum-master, respectivamente.

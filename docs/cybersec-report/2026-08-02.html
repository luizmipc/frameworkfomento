O que já está bem protegido

  • RESOLVIDO e reconfirmado — Dockerfile root + sem HEALTHCHECK (achados A021/A026, 2026-08-01): trivy continua reportando 0 misconfigurações no Dockerfile. docker inspect reporta healthy nesta rodada.
  • RESOLVIDO e reconfirmado — DEBUG/SECRET_KEY/ALLOWED_HOSTS/cookies (achados A022–A024, 2026-08-01): lidos de variável de ambiente com defaults seguros; fail-safe de SECRET_KEY seguem em vigor.
  • RESOLVIDO — achado-9 (1ª rodada): manage.py check --deploy não rodava de verdade. Correção aplicada: task A027, commit 87e2e0b — shortcuts/security-test.sh agora carrega .env (mesmo parsing linha a linha KEY=VALUE que run_tests.sh já usava, não source, porque DJANGO_SECRET_KEY contém caracteres como &()* que quebram sourcing de shell) antes de rodar o check. Confirmado nesta rodada: o comando roda de ponta a ponta e devolve 5 warnings honestos e esperados de ambiente de dev sem TLS (security.W004 HSTS, W008 SSL redirect, W012 session cookie secure, W016 CSRF cookie secure, W018 DEBUG=True) — todos coerentes com DJANGO_DEBUG=True no .env local, por design das tasks A022/A024 (esses controles só ativam quando DEBUG=False). Não há mais o warning de ALLOWED_HOSTS vazio (era W020 em rodadas anteriores) porque a task A024 já configurou um default (localhost,127.0.0.1). Isto é confirmação de que a auditoria tem visibilidade real sobre esse teste agora — não são "5 problemas novos", são os mesmos avisos de ambiente dev já contextualizados desde o achado-5 de 2026-08-01.
  • RESOLVIDO — achado-10 (1ª rodada): self-check de segurança da task A023 não era executado automaticamente. Esta não era uma saída de ferramenta do security-test.sh, e sim uma observação STRIDE (Detection) da 1ª rodada. Correção aplicada: task A028, commit 87e2e0b — run_tests.sh agora chama uv run python config/tests.py ao final da suíte. QA confirmou que o gate pega regressão real forçando uma falha no fail-safe do SECRET_KEY e revertendo em seguida — não é apenas "o código está lá", é "o gate realmente falha quando deveria". Fonte desta resolução: a task A028 em si (QA), não uma saída de ferramenta desta rodada — nenhum dos sete testes de security-test.sh mede isso diretamente.
  • RESOLVIDO — achado-11 (1ª rodada): Cross-Origin-Resource-Policy header ausente. Correção aplicada: task A029, commit 87e2e0b — app/config/middleware.py ganhou Cross-Origin-Resource-Policy: same-origin junto dos outros cabeçalhos já setados ali (Permissions-Policy, Cross-Origin-Embedder-Policy). Confirmado pela mesma ferramenta que achou o problema: a regra ZAP 90004 (família Cross-Origin-*) que gerava WARN-NEW na 1ª rodada agora aparece na lista de PASS ("Insufficient Site Isolation Against Spectre Vulnerability [90004]") — o ZAP subiu de 63 para 64 PASS nesta rodada, exatamente o esperado.
  • Melhoria real e mensurável em cabeçalhos HTTP, acumulada ao longo do dia — ZAP foi de 62 PASS/5 WARN-NEW (2026-08-01) → 63 PASS/4 WARN-NEW (1ª rodada, 2026-08-02) → 64 PASS/3 WARN-NEW (esta rodada). Os 3 WARN-NEW restantes seguem os mesmos, sem mudança de design: Server header (limitação do runserver de dev, não corrigível sem servidor de produção real), CSP (report-only por design da task A025, enforcement é decisão futura), Storable/Cacheable (informativo).
  • Zero segredos versionados, zero SAST, zero SCA relevante — gitleaks (64 commits, 0), bandit (0 Medium/High) e semgrep (0 findings) confirmam que o código-fonte segue limpo; trivy confirma 0 vulnerabilidades em app/uv.lock.
  • DAST baseline limpo de injeção — 0 FAIL em 4 URLs testadas; todos os WARN restantes são de cabeçalho ausente ou informativos, não injeção/autenticação/sessão quebrada.

Isto NÃO é uma afirmação de que toda a aplicação está segura — apenas que, dentro do que os sete testes de shortcuts/security-test.sh cobrem, nada de Crítico, Alto, Médio ou Baixo segue ativo nesta rodada. A aplicação ainda é majoritariamente o scaffold do Django, sem app de negócio implementado — a superfície real de ataque crescerá conforme features forem adicionadas.

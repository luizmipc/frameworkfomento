Achados

A02:2021 — Cryptographic Failures: SECRET_KEY do Django hardcoded em config/settings.py

🟡 Média — CVSS 5.9

O que foi encontrado: a SECRET_KEY usada pelo Django para assinar sessões, tokens CSRF e tokens de reset de senha está escrita em texto plano no código-fonte, com o prefixo django-insecure- — marcador padrão gerado por django-admin startproject, o que confirma que o valor nunca foi trocado por um segredo real gerenciado fora do controle de versão (ex.: variável de ambiente).

Evidência (saída literal do bandit — o valor real do segredo não é reproduzido aqui além do que a própria ferramenta já imprimiu; ver app/config/settings.py:23 para o valor completo):

>> Issue: [B105:hardcoded_password_string] Possible hardcoded password: 'django-insecure-...'
   Severity: Low   Confidence: Medium
   CWE: CWE-259 (https://cwe.mitre.org/data/definitions/259.html)
   Location: ./config/settings.py:23:13

Contexto adicional (leitura manual de app/config/settings.py, para confirmar o achado — não é um novo achado de ferramenta): a linha 23 não lê de variável de ambiente (os.environ/django-environ não estão em uso neste arquivo); o mesmo valor hardcoded seria usado em qualquer ambiente (dev, staging, produção) que rodasse este código sem alteração. Nota à parte: a linha 26 (DEBUG = True) também está hardcoded no mesmo arquivo — isso não é um achado de bandit (bandit não tem regra para DEBUG do Django; essa checagem é do manage.py check --deploy, não executado nesta rodada) e não está sendo classificado como achado aqui; é só uma observação de contexto para quando a suíte completa rodar.

Impacto: se o código-fonte for exposto a alguém que não deveria ter acesso a produção (colaborador removido, cópia de repo vazada, imagem Docker publicada com o arquivo embutido), quem tiver o valor da SECRET_KEY consegue forjar assinatura de sessão, token CSRF e token de reset de senha do Django — potencialmente sequestrando sessões de outros usuários ou disparando reset de senha arbitrário. Como o repositório é privado neste estágio e a chave não está publicada isoladamente (só dentro do próprio código), a exploração depende de uma etapa adicional de acesso ao código-fonte — por isso AC:High no CVSS abaixo, não Low.

CVSS 3.1: AV:N/AC:H/PR:N/UI:N/S:U/C:N/I:H/A:N = 5.9 (Média). Justificativa: sem acesso ao segredo em si o ataque não é possível (Confidentiality N — o achado não vaza a chave por si, é a existência da prática que é o risco), mas quem obtiver o valor tem Integridade Alta (forjar sessão/CSRF/reset de senha) sem precisar de privilégio ou interação do usuário alvo (PR:N, UI:N). Acesso ao código-fonte é uma pré-condição adicional (AC:H), não algo alcançável diretamente contra a aplicação rodando.

ASVS relevante: V6.4.1 (nível 1) — segredos e chaves criptográficas devem ser gerenciados fora do código-fonte versionado.

Recomendação: gerar uma SECRET_KEY nova e única por ambiente (dev/staging/produção), lida de variável de ambiente (ex.: os.environ["DJANGO_SECRET_KEY"], sem valor default hardcoded em produção), e remover o valor atual do histórico do git se o repositório algum dia tiver sido ou vier a ser público (rotação de chave é obrigatória nesse caso — chave antiga continua válida para forjar tokens enquanto não for trocada).

Prazo de remediação recomendado: até 60 dias (Média).

O que já está bem protegido

Honesto e restrito ao que bandit efetivamente escaneou (128 linhas de código Python em app/, 0 issues suprimidos via #nosec):

  • Nenhum uso de função perigosa clássica sinalizado por bandit nesta rodada — sem eval/exec sobre entrada externa, sem subprocess com shell=True, sem construção de SQL por concatenação de string, sem pickle/yaml.load inseguro — nenhuma dessas categorias apareceu no código atual (que ainda é majoritariamente o scaffold padrão do django-admin startproject, sem app de negócio implementado).
  • O único achado (1 issue, severidade "Low" na escala própria do bandit, confiança "Medium") é justamente o esperado para um projeto neste estágio de scaffold — bandit não encontrou nada além disso nas 128 linhas escaneadas.

Isto NÃO é uma afirmação de que o restante da aplicação está seguro — apenas que, dentro do que bandit cobre (SAST estático de Python), nada mais foi sinalizado. Segredos no histórico do git, dependências vulneráveis, configuração insegura de deploy e comportamento da aplicação rodando (XSS refletido, cabeçalhos HTTP, etc.) não foram avaliados nesta rodada — nenhuma conclusão pode ser tirada sobre eles a partir deste relatório.

Para quem resolver

  • Achado 1 — dev: mover SECRET_KEY para variável de ambiente, gerar valor novo por ambiente, e planejar rotação se o valor atual já tiver circulado fora do controle de acesso atual do repositório. Vira tarefa via /kanban-sync → "Criar nova tarefa" → "A partir de achados de segurança (docs/cybersec-report/)".

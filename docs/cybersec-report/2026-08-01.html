Relatório de Segurança — cybersecurity-blue

Auditoria de segurança da aplicação real (app/, Django 6.0.7, subida via docker compose up -d --build e confirmada respondendo em http://localhost:8000/ — HTTP 200), em 2026-08-01. Esta é a 3ª rodada do mesmo dia, registrada no mesmo documento (não um arquivo novo). Diferente das duas rodadas anteriores (ambas restritas a bandit), esta é a primeira vez que os sete testes de shortcuts/security-test.sh rodam sem argumentos — gitleaks, bandit, semgrep, auditoria de dependências, trivy, manage.py check --deploy e OWASP ZAP Baseline, na ordem canônica do script. Docker estava disponível e foi usado para subir a aplicação e rodar gitleaks/trivy/ZAP — nenhum teste foi pulado por falta de ferramenta nesta rodada.

Sumário executivo

Cinco testes (gitleaks, bandit, semgrep, trivy contra app/uv.lock) não encontraram nada de novo. Os dois testes que nunca tinham rodado contra superfícies novas — auditoria de dependências e manage.py check --deploy — encontraram achados reais, e o ZAP encontrou ausência de cabeçalhos de segurança HTTP. Nenhum achado desta rodada é Crítico ou Alto por CVSS puro; o mais grave em termos de exploitability real é o Dockerfile rodando como root (classificado Alta pelo trivy, tratado abaixo com o devido contexto).

Achados desta rodada

A05:2021 — Security Misconfiguration: Dockerfile roda como root

🟠 Alta — CVSS 7.0 (contextualizado)

Ferramenta: trivy (Dockerfile), regra DS-0002. O Dockerfile na raiz do repo (base ghcr.io/astral-sh/uv:python3.12-bookworm-slim) nunca declara um USER não-root; o processo Django (uv run manage.py runserver) roda como root dentro do container.

CVSS 3.1: AV:L/AC:L/PR:N/UI:N/S:C/C:H/I:H/A:H ≈ 7.0 (Alta) — cenário-base trivy assume escape de container completo. Contexto de exploração real: exige primeiro uma vulnerabilidade de execução de código (RCE) na própria aplicação ou em alguma dependência para sequer alcançar o processo root dentro do container — não é uma exposição diretamente explorável de fora hoje, já que nenhum RCE foi encontrado nesta rodada nem nas anteriores. É, ainda assim, um endurecimento de defesa em profundidade que reduz drasticamente o blast radius se outra vulnerabilidade aparecer no futuro (privilege escalation viraria trivial sem essa mitigação).

ATT&CK → D3FEND: encadeamento aproximado seria T1611 (Escape to Host) após um RCE inicial dentro do container (ex.: T1190, Exploit Public-Facing Application) — o container rodando como root remove uma barreira que dificultaria a escalada. Controle D3FEND: Harden — Container Hardening (D3-CH), via a diretiva USER não-root no Dockerfile.

A05:2021 — DEBUG=True hardcoded em produção potencial

🟡 Média — CVSS 6.5

Ferramenta: manage.py check --deploy, warning security.W018. DEBUG = True está hardcoded em app/config/settings.py (não lido de variável de ambiente, ao contrário de SECRET_KEY já corrigido na task A019) — deliberadamente fora do escopo daquela correção anterior. Se esse valor for para produção sem alteração, qualquer exceção não tratada expõe stack trace completo, variáveis locais, e a própria SECRET_KEY em uso.

CVSS 3.1: AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:L/A:N ≈ 6.5 (Média) — requer que uma exceção seja de fato disparada e alcançável remotamente para vazar a página de debug; hoje a aplicação é essencialmente o scaffold do Django (poucas rotas), o que limita a superfície imediata, mas não muda a classificação do controle em si estar ausente.

ASVS: viola V14.2 (configuração de produção deve divergir de dev nesse eixo). Não recebe tratamento ATT&CK→D3FEND detalhado por não ser Crítico/Alto, mas fica registrado: a técnica relevante seria T1592 (Gather Victim Host Information) via página de erro vazada.

A05:2021 — SECRET_KEY sem fallback seguro caso a env var não seja setada em produção

🟡 Média — CVSS 5.3

Ferramenta: manage.py check --deploy, warning security.W009. Isto não é uma regressão do achado da 1ª rodada (já corrigido pela task A019, commit 5db4142) — é um ângulo diferente que check --deploy cobre e que nenhum teste anterior tinha verificado: o fallback de dev em app/config/settings.py (os.environ.get('DJANGO_SECRET_KEY', 'django-insecure-dev-only-...')) ainda existe por design, para permitir rodar localmente sem configurar .env. O check --deploy não sabe distinguir "a env var está setada em produção" de "ninguém configurou a env var e o fallback inseguro está silenciosamente em uso" — ele sinaliza o valor default por conter o prefixo django-insecure-, que é exatamente o comportamento correto de um linter de config: soar o alarme para o cenário de configuração ausente.

CVSS 3.1: AV:N/AC:H/PR:N/UI:N/S:U/C:N/I:H/A:N ≈ 5.3 (Média) — só é explorável se alguém de fato esquecer de setar DJANGO_SECRET_KEY num deploy real; o mecanismo de mitigação (variável de ambiente) já existe e funciona, falta apenas uma trava que impeça o fallback de ser aceito fora de DEBUG=True.

ASVS: V6.4.1 continua atendido no caminho feliz (env var setada); esta é uma lacuna de "fail-safe" — o app deveria recusar subir com o fallback inseguro quando DEBUG=False.

A05:2021 — ALLOWED_HOSTS vazio e cabeçalhos/flags de transporte e sessão não endurecidos

🟢 Baixa — CVSS 3.1 (agrupado, 5 warnings)

Ferramenta: manage.py check --deploy, warnings security.W020 (ALLOWED_HOSTS = [] em app/config/settings.py), W004 (SECURE_HSTS_SECONDS não setado), W008 (SECURE_SSL_REDIRECT não é True), W012 (SESSION_COOKIE_SECURE não é True), W016 (CSRF_COOKIE_SECURE não é True). Agrupados porque todos compartilham a mesma causa raiz e o mesmo remédio: nenhum desses parâmetros foi configurado ainda porque a aplicação nunca rodou atrás de TLS/domínio real — são flags padrão de "checklist de deploy" do próprio Django, esperadas de estar pendentes numa aplicação que ainda só roda em localhost sem HTTPS.

CVSS 3.1 (pior caso do grupo, ALLOWED_HOSTS vazio permitindo Host header injection): AV:N/AC:H/PR:N/UI:N/S:U/C:L/I:L/A:N ≈ 3.1 (Baixa) — ALLOWED_HOSTS=[] na verdade bloqueia todo host em produção (comportamento fail-closed do Django quando DEBUG=False), então o risco real hoje é operacional (app não sobe corretamente atrás de proxy real) mais do que uma janela de exploração aberta; os quatro warnings de cookie/HSTS/SSL só importam quando a aplicação estiver de fato servida via HTTPS, o que ainda não é o caso.

ASVS: V14.2 (config de deploy) e V9.1 (comunicação segura) — nenhum viola hoje porque a aplicação ainda está em fase pré-deploy real; ficam registrados como pré-requisitos a resolver antes do primeiro deploy com domínio/TLS.

A05:2021 — Cabeçalhos de segurança HTTP ausentes (OWASP ZAP Baseline)

🟢 Baixa — CVSS 2.6 (agrupado, 4 WARN-NEW)

Ferramenta: OWASP ZAP Baseline, contra as 4 URLs testadas (/, /robots.txt 404, /sitemap.xml 404). Quatro alertas WARN-NEW: Server header vaza versão (10036), CSP não configurado (10038), Permissions-Policy ausente (10063), Cross-Origin-Embedder-Policy ausente/inválido (90004). Um quinto (Storable/Cacheable Content, 10049) é informativo, não um cabeçalho de segurança em si.

CVSS 3.1 (pior caso do grupo, ausência de CSP habilitando XSS refletido caso surja no futuro): AV:N/AC:H/PR:N/UI:R/S:U/C:L/I:L/A:N ≈ 2.6 (Baixa) — não há XSS confirmado hoje (0 achados de injeção no scan de 62 PASS); CSP é defesa em profundidade contra um XSS que ainda não existe no código atual (majoritariamente scaffold), não uma vulnerabilidade ativa. Vazamento de versão do servidor (Server header) facilita reconhecimento de atacante mas não é explorável sozinho.

ASVS: V14.4 (cabeçalhos de resposta HTTP). Resolução típica em Django: middleware django-csp ou configuração manual de SECURE_* headers, mais ServerHeader customizado no servidor WSGI real (não o runserver de dev usado neste teste, que sempre expõe versão).

A06:2021 — 3 CVEs em mcp, dependência transitiva de dev (via semgrep)

⚪ Informativa — CVSS base alto, exploitability real ≈ nula em produção

Ferramenta: auditoria de dependências (pip-audit via uv export). mcp 1.23.3 tem 3 CVEs conhecidas (PYSEC-2026-3481/3482/3483, fix em 1.27.2/1.28.1). Contexto de exploitability que muda tudo: mcp não é dependência do Django em produção — app/pyproject.toml declara apenas dependencies = ["django==6.0.7"] em [project]; mcp é dependência transitiva de semgrep (listada em [dependency-groups] dev = ["ruff", "bandit", "semgrep"], confirmado em app/uv.lock no bloco [[package]] name = "semgrep"). Ou seja: mcp nunca é importado pelo código Django, nunca roda em produção, e só existe na venv de desenvolvimento porque o próprio semgrep o usa internamente (provavelmente para seu recurso de servidor MCP). O vetor de ataque do CVSS-base de qualquer CVE em mcp pressupõe que um servidor/cliente MCP esteja de fato em execução e acessível — isso nunca acontece neste projeto fora de quando um humano roda semgrep manualmente numa máquina de dev, o que reduz o AV efetivo de Network para praticamente Local-com-ação-do-usuário e o risco real a desprezível. Nota: o próprio trivy escaneou app/uv.lock e não sinalizou nada (0 vulnerabilidades) — divergência esperada entre bases de dados/timing de atualização de ferramentas diferentes, registrada aqui com honestidade, não escondida.

ASVS: V14.2.1 tecnicamente não atendido no papel (dependência com CVE conhecida presente no lockfile), mas o requisito existe para proteger a superfície de produção, que este pacote nunca toca — por isso a classificação final é Informativa e é o achado de menor prioridade real desta rodada, apesar do CVSS-base de qualquer uma das três CVEs poder soar alto isoladamente.

A05:2021 — Dockerfile sem HEALTHCHECK

🟢 Baixa — CVSS 0 (higiene operacional, não vulnerabilidade)

Ferramenta: trivy (Dockerfile), regra DS-0026. Não é uma vulnerabilidade de segurança propriamente dita — é uma recomendação de disponibilidade/observabilidade (orquestradores conseguem detectar e reiniciar containers travados). Registrado por completude, sem CVSS atribuível.

Para quem resolver

Achados com correção de código/config real, para virar tarefa via /kanban-sync → "Criar nova tarefa" → origem "A partir de achados de segurança" (todos vão para o dev, não há agente de infra separado):

  • Alta: adicionar USER não-root ao Dockerfile (achado Dockerfile-como-root).
  • Média: configuração de produção — DEBUG=False via env var (mesmo padrão já usado para SECRET_KEY); recusar subir com o fallback de SECRET_KEY inseguro quando DEBUG=False.
  • Baixa: configurar ALLOWED_HOSTS, SECURE_HSTS_SECONDS, SECURE_SSL_REDIRECT, SESSION_COOKIE_SECURE, CSRF_COOKIE_SECURE — todos dependem de a aplicação estar de fato atrás de domínio real com TLS antes de fazer sentido ativar (ativar SECURE_SSL_REDIRECT/cookies seguros sem TLS quebra a aplicação em dev); registrar isso na tarefa para não virar um "liga tudo" cego. Cabeçalhos HTTP do ZAP (CSP, Permissions-Policy, Cross-Origin-Embedder-Policy, ocultar versão do servidor) e HEALTHCHECK no Dockerfile também entram aqui.
  • Informativa: atualizar semgrep (que puxaria mcp mais novo) quando conveniente — não é urgente dado que nunca toca produção; não recomendado abrir tarefa dedicada só para isso, pode ir junto de uma atualização de rotina de dependências de dev.

Nenhuma decisão de compliance formal (ex.: LGPD) nem de release-readiness sai deste relatório — isso é do product-owner e do scrum-master, respectivamente.

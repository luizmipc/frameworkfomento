O que já está bem protegido

Honesto e restrito ao que bandit efetivamente escaneou (132 linhas de código Python em app/, 0 issues suprimidos via #nosec):

RESOLVIDO — A02:2021 — Cryptographic Failures: SECRET_KEY do Django hardcoded em config/settings.py (achado original da 1ª rodada, 2026-08-01)

🟡 Média — CVSS 5.9 (histórico) → ✅ Corrigido

Histórico do achado (1ª rodada): a SECRET_KEY usada pelo Django para assinar sessões, tokens CSRF e tokens de reset de senha estava escrita em texto plano no código-fonte, com o prefixo django-insecure- (marcador padrão de django-admin startproject), confirmando que o valor nunca tinha sido trocado por um segredo real gerenciado fora do controle de versão. bandit sinalizou como [B105:hardcoded_password_string] / CWE-259, em app/config/settings.py:23. CVSS 3.1 original: AV:N/AC:H/PR:N/UI:N/S:U/C:N/I:H/A:N = 5.9 (Média) — ver justificativa completa preservada no histórico do git deste documento (git log -p docs/cybersec-report/2026-08-01.html).

Correção aplicada e confirmada nesta 2ª rodada: task A019, aprovada pelo QA, commit 5db4142 em main. SECRET_KEY agora é lida via os.environ.get("DJANGO_SECRET_KEY", <fallback marcado como dev-only>), com .env/.env.example criados e docker-compose.yml/Dockerfile parametrizados para injetar o valor real por ambiente. bandit não sinaliza mais B105 nesta linha — 0 achados nesta 2ª rodada, nas mesmas 132 linhas de código Python.

Ressalva honesta: esta rodada confirma apenas que o código-fonte Python não tem mais o valor hardcoded (o que bandit consegue ver). Não confirma que o .env real de produção esteja fora do controle de versão nem que o fallback de dev não vaze para produção por engano — essas checagens são de gitleaks (segredos versionados) e de manage.py check --deploy/revisão manual de config de deploy, nenhum dos dois executado nesta rodada. ASVS V6.4.1 é atendido no que bandit pode verificar; validação completa do requisito depende dessas checagens ainda pendentes.

  • Nenhum uso de função perigosa clássica sinalizado por bandit nesta rodada — sem eval/exec sobre entrada externa, sem subprocess com shell=True, sem construção de SQL por concatenação de string, sem pickle/yaml.load inseguro — nenhuma dessas categorias apareceu no código atual (que ainda é majoritariamente o scaffold padrão do django-admin startproject, sem app de negócio implementado).
  • Zero achados nesta 2ª rodada nas 132 linhas escaneadas — inclusive o achado único que existia na 1ª rodada foi corrigido e confirmado resolvido, como detalhado acima.

Isto NÃO é uma afirmação de que o restante da aplicação está seguro — apenas que, dentro do que bandit cobre (SAST estático de Python), nada foi sinalizado nesta rodada. Segredos no histórico do git, dependências vulneráveis, configuração insegura de deploy e comportamento da aplicação rodando (XSS refletido, cabeçalhos HTTP, etc.) não foram avaliados nesta rodada — nenhuma conclusão pode ser tirada sobre eles a partir deste relatório.
